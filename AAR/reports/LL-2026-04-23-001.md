## Executive Summary - Top 3 Lessons
1. Ashita v3 classic uses _addon.name + ashita.register_event; v4 uses addon.name + ashita.events.register. Silent stalls at load stage 2/3 when mismatched.
2. When an addon has NO console/chat output, a file-based io.open() trace log at each step is the fastest diagnostic path.
3. Before coding any new Ashita Lua addon, dump a known-working addon (distance.lua, tparty.lua) first to confirm which API flavor the runtime expects.

## 3. Root Cause Analysis
PRIMARY: ai_bridge.lua was coded against the Ashita v4 Lua API (addon.name, ashita.events.register, chat.header/error, T{} table wrapper), but the deployed Ashita runtime at F:\ffxi\Ashita is the original Ashita v3 CLASSIC (atom0s 2014-2017 branch) which uses a different API surface: _addon.name globals, ashita.register_event (no .events.), no chat module, plain Lua tables. 

WHY SILENT: top-level require() calls succeeded (Ashita v3 classic happens to also expose an ashita global), so stage (2) Lua-chunk-executed completed cleanly. The load event registration line `ashita.events.register('load', 'ai_bridge_load', fn)` evaluated to nil-index on the missing events subtable, but Ashita caught the error inside the addon boot harness without surfacing any [E] line to the debug log. No chat print, no Lua traceback in console, no crashlog. The only symptom was the absence of the 'Addon load. (3) - ai_bridge' line. 

CONTRIBUTING: (a) the original v4 ai_bridge.lua had no runtime version assertion (`assert(_addon, 'expected Ashita v3 classic')`) that would have failed loudly; (b) before coding, no working addon was dumped from the deployed Ashita to confirm which API flavor the runtime expects; (c) the two API flavors use overlapping global names (`ashita`, `AshitaCore`) which made it easy to assume they were compatible.

## 4. Attempts That Failed
**Attempt:** Assume socket.bind was failing (port in use, addr bind error)
- Reasoning: Initial hypothesis for 'listening never prints' is always bind failure.
- Why failed: PORT_CHECK2 showed 27115 DOWN and no process holding it. trace log later confirmed bind succeeded cleanly — the handler never fired at all.
- Learned: When stage (2) never advances to (3), the handler isn't running; don't waste time instrumenting the bind itself.

**Attempt:** Suspect require('json') resolving to nil due to nested libs/json/json.lua path
- Reasoning: The addon wraps json load in pcall and tolerates nil, but maybe some downstream code blew up on missing json.
- Why failed: json is only used in request/response encode/decode, not in load handler. The load handler would fire before any request arrived. Moreover the rewrite uses require('json.json') explicitly and works.
- Learned: pcall-wrapped requires are fine to leave broken if the addon tolerates nil; don't chase them when stage (3) never reaches.

## 5. Solutions That Worked
**Dump a working Ashita addon to learn the real API surface** _(source: internal-reference)_
LIBS_DUMP.ps1 + V3_REF.ps1 printed full contents of distance.lua and tparty.lua. Both start with `_addon.name = '...'`, then `require 'common'`, then `ashita.register_event('load', function() ... end)`. This is the v3 classic pattern. No `addon.name`, no `ashita.events.register`, no `chat.header`.

**Rewrite ai_bridge.lua for v3 classic API** _(source: derived)_
Replaced `addon.*` → `_addon.*`, `ashita.events.register(evt, id, fn)` → `ashita.register_event(evt, fn)`, `chat.header/error` → plain `print(...)` and io.open-based trace file, `T{}` → plain Lua `{}`, `require('json')` → `require('json.json')`, `AshitaCore:GetMemoryManager():...` → `AshitaCore:GetDataManager():...`, `AshitaCore:GetChatManager():QueueCommand(txt, 1)` for send_text.

**File-based trace log for silent addon failures** _(source: invented)_
At the top of the addon and inside the load/unload handlers, `local f = io.open('F:\\ffxi\\Ashita\\logs\\ai_bridge_trace.log', 'a'); f:write(...); f:close()`. Works even when print() output is suppressed, chat manager is not yet available, or errors are eaten by Ashita's addon harness.

**Non-blocking socket poll via render event** _(source: derived)_
ashita.register_event('render', fn) fires every frame. Inside: accept() with settimeout(0), then for each client pump receive(1024), split on newlines, dispatch JSON-RPC. Never blocks the game thread.

## 8. Warfighter Analysis
- **Foreseeable:** YES. Ashita v3 classic and v4 fork have publicly documented API differences. A 15-second check of a working addon's source would have revealed the flavor.
- **Red Team (wrong assumptions):** Assumed the Ashita install was modern/v4 without verification. Assumed silent stall meant bind failure rather than event-registration failure.
- **Blue Team (what worked):** Ashita debug log told us exactly where execution stopped (stage 2 vs 3). Working addon sources (distance.lua, tparty.lua) were on disk and readable. File trace log pattern was invented on the spot and paid for itself immediately.
- **White Team (overall):** Debug session was efficient once the API mismatch was named. Total wall-clock from 'port still DOWN' to 'SMOKE : up' was ~20 minutes.
- **Vulnerability score:** WEAK - The failure mode was silent — no error, no crash, no alert. Only a missing log line. Without the file trace log invention, this could have burned hours.
